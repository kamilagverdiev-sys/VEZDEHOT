Это два origin в одном браузере компьютера, а не испытание на двух физических устройствах. Настоящий Telegram Mini App вход и связывание способов входа остаются отдельной приёмкой.

## Google

1. В Google Cloud → Google Auth Platform настройте Branding, Audience и контакт владельца. Проверьте статус публикации, выбранную аудиторию и доступность входа для нужных пользователей с фактически запрошенными scopes.
2. Создайте OAuth Client типа **Web application**. Добавьте production-origin Vercel и Sites в Authorized JavaScript origins, а callback Supabase из таблицы — в Authorized redirect URIs.
3. В Supabase → Authentication → Sign In / Providers → Google включите провайдер и сохраните полученные Client ID и Client Secret. Достаточно scopes `openid`, `email`, `profile`.
4. Добавьте оба конечных redirect приложения в Supabase → URL Configuration.
5. Пройдите реальный вход тестовым аккаунтом, выход и повторный вход, затем проверьте восстановление собственного профиля.

Публичный `GET https://cyzbraifdkrqicdsbuwe.supabase.co/auth/v1/settings` с заголовком `apikey` существующего publishable key позволяет приложению обнаружить `external.google`. До подтверждённого `true` интерфейс сообщает, что Google ещё не подключён; при недоступности настроек гостевой режим остаётся доступен.

Кнопка обновляется и в уже открытом профиле после ответа настроек. Параллельные попытки входа запрещены, чтобы второй PKCE-запрос не заменял подтверждение первого. Возврат должен происходить в том же браузере и на том же устройстве, где начат вход: переносить `auth-callback.html?code=…` на другой телефон или ПК нельзя. На втором устройстве выполняется новый вход в тот же аккаунт.

Перед OAuth-переходом приложение проверяет, удалось ли сохранить текущий профиль на устройстве. При запрете хранилища или переполнении оно остаётся на текущей странице и предлагает разрешить хранилище сайта или освободить место. После исправления можно повторить вход: несохранённый гостевой прогресс сначала записывается, затем начинается OAuth. Это предотвращает уход со страницы с профилем, который существует только в памяти; успешная запись профиля сама по себе ещё не доказывает исправность настроек Google или завершение PKCE.

При отмене, просроченном подтверждении или ошибке PKCE страница завершения сообщает об ошибке, даже если в браузере сохранилась другая, ранее открытая сессия. Технический `error_description` провайдера не выводится пользователю. Код и фрагмент очищаются из адресной строки после завершения проверки.

Client Secret введён владельцем непосредственно на [странице Google-провайдера Supabase](https://supabase.com/dashboard/project/cyzbraifdkrqicdsbuwe/auth/providers?provider=Google); провайдер включён. При последующем изменении настройки секрет следует вводить там же, без передачи в чат или Git. На момент настройки подключённый Supabase connector не предоставлял операции изменения Auth configuration; сам факт доступа к таблицам не даёт Google OAuth credentials.

Дополнительно проверены проекты CRM/FORMA. Production CRM использует отдельный Supabase `znoafaphmqtlwyuskhkb`; доступ к его управлению через текущий connector отклонён. В репозитории есть компонент Google OAuth, который проверяет доступность провайдера, но наличие компонента не подтверждает работающую конфигурацию. В metadata переменных Vercel нет Google OAuth credentials, значения секретов не экспортировались. Настройка CRM не переносилась в VEZDEHOT.

## Telegram Mini App: вход внутри бота

`VesdehotBot` открывает игру внутри Telegram. При наличии `Telegram.WebApp.initData` клиент отправляет **только подписанную строку** в `https://cyzbraifdkrqicdsbuwe.supabase.co/functions/v1/telegram-auth`. Edge Function проверяет Ed25519-подпись Telegram, bot ID `8412086640` и время данных, сопоставляет проверенный Telegram ID с Supabase user ID и возвращает одноразовый `token_hash`. Клиент завершает вход через `auth.verifyOtp({token_hash, type: 'magiclink'})`. `initDataUnsafe` не является доказательством личности и не используется.

В `dist/auth-config.js` для этого пути находятся публичные `telegramMiniAppEnabled: true` и `telegramAuthUrl`. Функция должна быть опубликована с `verify_jwt: false`: вход проверяется подписью Telegram, а у гостя ещё нет пользовательского JWT. CORS разрешает только Vercel и Sites из таблицы; серверные права Supabase остаются в окружении Edge Function. Доверенная метка `app_metadata.telegram_id` используется для отображения подключённого Telegram.

В обычном браузере кнопка **«Открыть в Telegram»** открывает `https://t.me/VesdehotBot` и объясняет подтверждение внутри бота. Открытие ссылки само по себе не авторизует пользователя. Подписанные данные появляются при запуске игры через Telegram; SDK сообщает готовность событием `vezdehot:telegramready`, после которого интерфейс обновляет доступность входа.

Этот способ не объединяет уже открытый Google/OIDC-аккаунт с Telegram. Сначала нужно выйти; профили остаются отдельными. Для явного связывания способов используйте OIDC и manual identity linking, описанные ниже. Настоящий успешный вход проверяется внутри Telegram, а не подстановкой клиентского `user.id`.

Клиент различает просроченные или неверные данные Telegram, ограничение частоты, сетевую ошибку и сбой сервера; сообщения предлагают соответствующий следующий шаг без вывода подписанной строки или токенов. Ошибка интерактивного входа привязана к исходному профилю и очищается при переходе к другому аккаунту; ошибка проверки callback не скрывается ранее сохранённой сессией. Автоматические сценарии этих ошибок проверены 26 октября, настоящий успешный Mini App вход остаётся отдельной приёмкой.

## Telegram: дополнительный браузерный OAuth / OIDC

1. В BotFather выберите бота (или создайте бота проекта), откройте **Login Widget** и настройку **OIDC**. Зарегистрируйте точный Redirect URI Supabase из таблицы. Получите OIDC Client ID и Client Secret; это не публичные настройки сайта.
2. В Supabase → Authentication → Providers → **New Provider** выберите **Auto-discovery (OIDC)**. Укажите выданные BotFather Client ID и Client Secret в соответствующих полях Dashboard.
3. Используйте следующие значения провайдера:

| Поле | Значение |
| --- | --- |
| Provider type | `oidc` |
| Identifier | `custom:telegram` |
| Name | `Telegram` |
| Issuer | `https://oauth.telegram.org` |
| Scopes | `openid`, `profile` |
| Email optional | `true` |
| PKCE enabled | `true` |
| Skip nonce check | `false` |

Telegram не предоставляет email, поэтому `email_optional` обязателен. Телефон и разрешение боту писать пользователю для входа не нужны. Supabase проверяет OIDC-токен и хранит secret; отдельный Telegram token exchange в статическом клиенте не требуется.

В публичном `dist/auth-config.js` флаг **`telegramEnabled`** должен оставаться `false`, пока OIDC-провайдер не настроен; это отдельный флаг от `telegramMiniAppEnabled`. Включайте его только после настройки и проверки перехода. Этот файл содержит только публичные параметры и флаги; не помещайте туда Client Secret, bot token, Supabase secret key или `service_role`. Не считайте наличие кнопки или флага доказательством успешной авторизации.

## Один профиль, разные способы входа

Для OIDC в Supabase рекомендуется включить **Manual Identity Linking**, затем установить публичный `manualLinkingEnabled: true`. Подключайте второй способ через `auth.linkIdentity()` только из уже открытого аккаунта. Telegram и Google не объединяются автоматически по email: у Telegram email нет. Обычный повторный `signInWithOAuth()` может открыть другой аккаунт. Нативный Mini App путь не вызывает `linkIdentity()` и не объединяет аккаунты автоматически.

Локальный гость хранится отдельно от каждого `auth.uid()`. При входе существующее облачное сохранение имеет собственную историю; нельзя автоматически записывать поверх него общий браузерный snapshot или складывать балансы. Перенос гостевого прогресса допустим в новый профиль без сохранений, а при конфликте нужен явный выбор. При выходе восстанавливается гостевой профиль, а не данные предыдущего аккаунта. На Vercel и Sites разные браузерные хранилища: общими для них становятся профиль и пять сохранённых партий после входа в тот же аккаунт и подтверждённой синхронизации. Все состояния переносятся вместе с балансом; при разных локальных ветках нужен явный выбор облачной версии.

Анонимный Supabase Auth для локального гостя включать не обязательно. Если позднее используется `signInAnonymously()`, переход к постоянному аккаунту делается через `linkIdentity()`; анонимный пользователь получает PostgreSQL-роль `authenticated`, а не `anon`.

## Настоящая проверка телефон → ПК

Проводить на тренировочной партии владельца, с одним способом входа на обоих устройствах. Текущий нативный Telegram-вход требует запуска Mini App внутри Telegram: на ПК откройте `VesdehotBot` в клиенте Telegram, который поддерживает Mini Apps. Открытие обычной ссылки сайта в браузере не переносит Telegram-сессию. Для независимого браузерного входа уже доступен Google; Telegram OIDC требует отдельной настройки. Смешивать Google и нативный Telegram как один аккаунт нельзя.

1. На телефоне войти, открыть профиль и дождаться подтверждения облачного сохранения. Записать имя, баланс, XP и короткий ID аккаунта из раздела способов входа, без копирования токенов. Этот ID нужен только для сверки профиля и не является кодом для авторизации.
2. Начать одну партию, сделать ход и поставить на паузу. В профиле дождаться нового подтверждённого сохранения. Не закрывать вкладку в состоянии «Сохраняем» или «Нет сети».
3. На ПК заново войти **тем же способом и в тот же аккаунт**. Сверить короткий ID в профиле, имя, баланс, XP, затем продолжить ту же партию: карты/роли/собственность, очередь, банк и номер раздачи должны совпадать. Разные ID означают разные аккаунты; одинаковый ник не доказывает, что вход выполнен в один профиль. Автоматического хода сразу после восстановления быть не должно.
4. Сделать ход на ПК, сохранить и вернуться на телефон. Если телефон успел изменить свою ветку, должен появиться конфликт с паузой; принятие облачной версии предварительно архивирует местную ветку.
5. Завершить партию на одном устройстве. На другом проверить ровно одну запись результата и одно начисление. Перезагрузка и повтор синхронизации не должны менять награду.
6. Выйти: должен открыться отдельный гостевой профиль. Войти повторно: возвращается прежний аккаунт. Повторить перенос для всех пяти игр и отдельно для каждого используемого production-origin.

Фиксировать только фактический результат, браузер/версию Telegram, дату и origin. Не включать access token, refresh token, `initData` или одноразовый код в отчёт. Сейчас полный сценарий на двух физических устройствах остаётся ручной приёмкой. Подтверждённые выше вход, выход, повторный вход и продолжение серверного Дурака между двумя origin в одном Edge не заменяют эту проверку.

## Отдельные серверные столы

Серверные Дурак, Покер, Бункер, Мафия и Монополия используют тот же подтверждённый аккаунт, но собственные состояния и квитанции действий. Их ходы не входят в общий checkpoint пяти обычных игр и не меняют его баланс практики или XP. Реализован и локально проверен отдельный [серверный баланс](SERVER_ECONOMY.md): бесплатный стол по умолчанию или вход за 100 V, серверный расчёт результата и суточный бонус. Гостевой импорт и старые checkpoints не пополняют этот баланс. Первоначальная миграция кошелька и три Edge Function для Дурака, Покера и баланса развёрнуты 25 октября; версии и проверки указаны в контракте. Расширение для [Бункера](SERVER_BUNKER.md) развёрнуто 27 октября: `server-bunker` v1, `server-wallet` v2 и закрытые таблицы состояния/квитанций. Проверки SQL и всей цепочки клиента/Edge/движка/SQL прошли в изоляции. Серверная часть [Мафии](SERVER_MAFIA.md) также развёрнута 27 октября: миграция `20261027094910`, `server-mafia` v1 и `server-wallet` v3; обе функции требуют JWT, новые таблицы и RPC закрыты от браузерных ролей. Интерфейс прошёл изолированную браузерную приёмку на 320/390/844/1440 px и опубликован на обоих адресах. Под настоящим аккаунтом владельца пройдена полная бесплатная Мафия, подтверждены перезагрузка, повторная партия и продолжение между origin в обе стороны; баланс остался 1 000 V. Серверная часть [Монополии](SERVER_MONOPOLY.md) развёрнута: миграция `20261027122154`, `server-monopoly` v1 и `server-wallet` v4 требуют JWT, новые таблицы и RPC закрыты от браузерных ролей. Пакет интерфейса v28 опубликован на Vercel и Sites, исходники синхронизированы с GitHub. Перед публикацией успешно прошли автоматические тесты, шесть SQL-наборов, семь групп интеграционных сценариев и изолированная браузерная приёмка на 320/390/844/1440 px. Её состояние и внутриигровые деньги также отделены от общего клиентского checkpoint. Тестовый аккаунт браузерного стенда не подтверждает настоящий вход владельца; в текущем запуске подключённый локальный браузер не предоставил исходный контекст, поэтому авторизованная production-приёмка Монополии не проводилась.

В v29 добавлена сводка пяти серверных игр в лобби. Она отправляет только запросы чтения и хранит краткие проверенные данные в памяти вкладки для текущего аккаунта; повторное отображение лобби может использовать эту сводку до обновления. Смена аккаунта, потеря управления или скрытие вкладки очищают её; поздний ответ прежнего аккаунта не отображается. Сводка не хранит карты и роли, не восстанавливает незавершённые мутации и не меняет баланс. Если на устройстве остался неподтверждённый запрос, игрок открывает соответствующую игру для его проверки. Возврат из серверного стола использует `?view=lobby`, чтобы сначала открыть список игр, не возобновляя другую обычную партию.

Также в v29 исправлен фоновый запуск контроллера Дурака: последовательность «скрытая вкладка → обновление профиля → возврат» загружает актуальный стол и при необходимости восстанавливает тот же неподтверждённый ход. В Покере, Бункере, Мафии и Монополии обновление кошелька привязано к проверенной версии стола или квитанции хода; подтверждённый расчёт вызывает чтение баланса даже при сбое следующей загрузки стола. Недостаток средств также вызывает повторное чтение кошелька. Эти изменения проверены автоматическими регрессиями и изолированной браузерной сводкой на ширинах 320–1440 пикселей; они не являются результатом нового теста под настоящим аккаунтом.

Перенос серверного стола проверяется отдельно: дождаться подтверждения действия в самом столе, на втором устройстве войти в тот же аккаунт, открыть тот же серверный режим и загрузить его текущую версию. Для Покера сверить номер раздачи и стеки, затем перейти к следующей раздаче без второго входного списания. Для Бункера сверить раунд, раскрытые характеристики, выбывших кандидатов и сохранённые голоса; выбранная, но ещё не подтверждённая карта или кандидат остаются локальным выбором интерфейса. Для Мафии сверить собственную роль, фазу ночи/дня, живых игроков, собственные проверки комиссара, пометки и историю голосов; чужие закрытые роли не должны появляться после восстановления. Для Монополии сверить номер хода, очередь, кости, позиции, наличные, собственность и фазу покупки/разбора; повтор загрузки не должен перебрасывать кости. Для стола за 100 V сверить серверный баланс, завершить партию и убедиться, что повтор запроса/перезагрузка не создают вторую выплату. Серверный баланс перечитывается отдельно от состояния стола. 27 октября бесплатный серверный Дурак проверен между Vercel и Sites в одном локальном Edge: исходная рука совпала, ход на Sites и ответ бота загрузились на Vercel, завершение захода на Vercel и второй раунд загрузились на Sites. Монеты и XP в бесплатном режиме не изменились. Отдельно 27 октября бесплатный серверный Бункер продолжен между теми же origin: подтверждённое раскрытие и первый итог голосования совпали, переход на Sites ко второму раунду загрузился на Vercel; серверный баланс остался 1 000 V. Это продолжение одной незавершённой партии, а не приёмка полного платного расчёта. В Мафии также подтверждено продолжение между origin в обе стороны: сохранённые собственная роль, ночная фаза и пометка, затем переходы рассвета и дня. Бесплатная партия завершена победой мирной команды во втором раунде, результат пережил перезагрузку; повторная партия создала новую раздачу. Баланс остался 1 000 V. Настоящая проверка телефон → ПК, production-приёмка серверных Покера и Монополии, расчёт стола за 100 V ещё требуют отдельной приёмки.

Общий внутренний transport у `VEZDEHOT.serverDurakRequest()`, `VEZDEHOT.serverPokerRequest()`, `VEZDEHOT.serverBunkerRequest()`, `VEZDEHOT.serverMafiaRequest()`, `VEZDEHOT.serverMonopolyRequest()` и `VEZDEHOT.serverWalletRequest()` допускает только фиксированный endpoint соответствующего сервиса на настроенном Supabase-проекте. Перед отправкой он получает актуальную Supabase session и сверяет владельца; после ожидания сети и чтения ответа снова проверяет аккаунт и активную вкладку. Access token не возвращается игровому интерфейсу и не добавляется в его сохранения. Ответы, пришедшие после смены аккаунта или потери управления вкладкой, отклоняются.

## Проверка перед объявлением входа готовым

На страницах локальный `vendor/supabase-2.118.0.js` загружается перед `auth-config.js`, затем общие валидаторы, `game-store.js`, `tab-session.js`, `cloud-checkpoint.js` и `platform.js`. Для production включён `checkpointsEnabled`; запись профиля и результатов выполняется только через атомарный RPC, описанный в [контракте сохранений](CLOUD_CHECKPOINT_CONTRACT.md). Доступ к профилю и запуск сохранённых игр выполняется после `VEZDEHOT.ready`. При событии `vezdehot:accountchange` игра останавливает таймеры; общий API замораживает мутации до перехода в лобби. Регрессионные тесты: `node tests/platform-auth.cjs`.

Полный локальный прогон 26 октября: `node --test tests/*.cjs` — **452 теста, 452 успешных**, без пропусков. Он включает готовность callback, ошибки входа и изоляцию архивов. Это исторический автоматический прогон; реальная проверка Google-входа 27 октября описана отдельно выше и не меняет его состав или число тестов.

- Оба провайдера возвращают на разрешённый callback без секретов в URL/коде сайта; отмена и ошибка оставляют понятное сообщение и доступ к гостевому режиму.
- Сессия подтверждена Supabase, повторное открытие сохраняет вход, выход не показывает чужой профиль.
- Аккаунты A и B на одном браузере не видят и не перезаписывают локальные или облачные данные друг друга, включая медленный ответ сети при переключении.
- Чтение профиля защищено RLS по `auth.uid()`, изменения проходят owner-only checkpoint RPC с проверкой серверной версии. Прямая запись клиентом в `profiles` и `player_results` запрещена. `user_metadata` не используется для прав доступа.
- Подключение Google и Telegram из одного аккаунта сохраняет тот же user ID. Конфликт уже существующей identity обрабатывается сообщением, без скрытого слияния профилей.
- В Telegram Mini App реальная подпись принимается сервером; неверная/просроченная отклоняется. Обычный браузер предлагает открытие бота, а не выдуманную авторизацию. Подтверждение Native Mini App и связывание OIDC проверяются отдельно.

### Повтор подтверждения и вход в лобби (v30)

Все пять игровых клиентов и бонус кошелька допускают отсутствие локальной записи только при завершении уже проверенного запроса из памяти. Это восстанавливает редкий сценарий «удаление прошло, контрольное чтение упало»; непустая заменённая запись не удаляется. Поздний ответ при смене аккаунта или управления отбрасывается как раньше.

Параметры `view=lobby` и допустимый `game` задают только входной экран и после принятия активной вкладкой удаляются из URL. Последующая перезагрузка восстанавливает выбранную игру; прочие параметры, история и якорь сохраняются. Пока вкладка не получила управление, параметры остаются для её предстоящей перезагрузки.

В текущем запуске подключение Browser повторно вернуло `originating browser context`. Дополнительных разрешений от владельца не требуется, но настоящая авторизованная проверка и физический телефон → ПК не выполнены. Изолированная интеграция финального расчёта Монополии моделирует два независимых хранилища и не использует аккаунт владельца.
