# Первый серверный стол: Дурак

Это отдельная партия с ботами и проверкой действий на сервере. Бесплатная практика остаётся по умолчанию; необязательный вход за 100 V использует отдельный защищённый [серверный баланс](SERVER_ECONOMY.md). Вход и расчёт результата сохраняются атомарно с партией и квитанцией. Пять обычных игр, их баланс практики и общий checkpoint остаются самостоятельными. Расширение экономики реализовано и проверено; серверное развёртывание описано в [контракте кошелька](SERVER_ECONOMY.md).

## Правила и состояние

- Edge Function `server-durak` создаёт колоду с `crypto.getRandomValues`, раздаёт карты, выбирает ходы ботов и выполняет переходы правил.
- `core.mjs` генерируется из функций обычного Дурака в `dist/index.html`: `node scripts/sync-server-durak-core.cjs`. Тест `--check` не разрешает расхождение копии. Сначала изменяются и проверяются общие исходные правила, затем обновляется генерация.
- В запросе нельзя передать состояние, место игрока, исход или награду. Игрок всегда занимает место 0; сервер проверяет фазу, очередь, наличие карты, возможность защиты/подкидывания, лимит стола и завершение раунда.
- Действия человека `finish` («Бито») и `take` («Забрать») сразу завершают текущий раунд: подготовка и `durakCommitRound` выполняются в одном действии. Карты уходят в отбой или в руку, выполняются добор и смена очереди; если партия закончилась, в тот же commit входит её итог. Промежуточная фаза `roundEnd` не сохраняется и второй HTTP-запрос от клиента не нужен. Обычный Дурак использует такую же последовательность без промежуточного локального сохранения.
- Сохранённая ранее фаза `roundEnd` по-прежнему завершается через `continue`. Раунды, подготовленные ботами, могут оставаться на явном разборе. Учебная финальная позиция сохраняет отдельные шаги подготовки и переноса карт; общие функции правил не изменены.
- Колода и руки ботов находятся только в закрытой схеме. Ответ содержит руку игрока, открытые пары, известный козырь, размеры скрытых рук и колоды. Даже после завершения партии сервер не раскрывает скрытые карты.
- Пока человек играет, бот выполняет не более двух переходов на запрос, до следующего хода игрока или явной паузы для разбора. После выхода человека без карт и при пустой колоде оставшиеся боты доигрывают текущую партию обычными переходами правил (защитный лимит — 512). Игроку не нужно докликивать чужие ходы. Фоновая вкладка не двигает стол сама.
- При сдаче до выхода игрока текущий стол завершается поражением. После выхода без карт интерфейс предлагает только продолжение до итогов; старый запрос `resign` в таком состоянии трактуется как `continue` и не отнимает заработанный результат. Новый стол можно создать только после завершённого. Существующий локальный Дурак остаётся отдельным сохранением.

## Экономика

Старт принимает `stake: 0 | 100`; отсутствие поля и старое сохранение без `economy` означают бесплатную практику. Вход за 100 V списывается один раз. Победа возвращает `100 × число игроков`, ничья — 100 V, поражение или сдача — 0. XP за эти исходы: 80/40/25/0. Сдача учитывается как завершённая проигранная партия без XP. Бесплатный стол не меняет серверный баланс, XP или статистику. SQL проверяет завершение партии и пересчитывает выплату из серверного состояния.

## API

`POST https://cyzbraifdkrqicdsbuwe.supabase.co/functions/v1/server-durak`

Требуются `Content-Type: application/json`, публичный `apikey` проекта и `Authorization: Bearer <access_token>` текущего постоянного аккаунта. Секрет сервера не передаётся клиенту. Разрешены ровно два production-origin VEZDEHOT.

| Операция | Тело |
| --- | --- |
| Прочитать | `{ "op": "load" }` |
| Создать | `{ "op": "start", "actionId": "UUID", "expectedRevision": 0, "bots": 1, "difficulty": "normal", "stake": 0 }` |
| Сыграть карту | `{ "op": "action", "actionId": "UUID", "expectedRevision": 1, "gameId": "UUID", "action": { "type": "attack", "cardId": "6♠" } }` |
| Иное действие | Такой же конверт с `action: { "type": "continue" }` |

Допустимые действия: `attack`, `defend`, `take`, `finish`, `continue`, `resign`. Поле `cardId` требуется только для атаки и защиты. `game.legal.actions` и `game.legal.cards` содержат доступный выбор, однако сервер проверяет его заново при каждом запросе.

Один `finish` или `take` увеличивает ревизию один раз. После завершения раунда сервер выполняет обычную ограниченную работу ботов, поэтому ответ уже может содержать их следующую атаку. Клиент отображает возвращённое состояние и не отправляет дополнительный `continue` автоматически. Повтор потерянного ответа использует исходный `actionId`: он не должен забирать карты уже следующего раунда или повторно начислять итог.

Ответ: `{status: "ok" | "saved" | "conflict", revision, game}`. `game` равен `null`, если стол ещё не создан. Ревизия монотонна на аккаунт и не сбрасывается при новой партии. `game.economy` содержит `{version, stake, settled, payout, xp, outcome}`; суммы задаёт сервер. После подтверждения действия клиент отдельно перечитывает кошелёк, поэтому старая игровая квитанция не устанавливает старый баланс.

HTTP-коды: 400 — неверное тело; 401 — нужен постоянный аккаунт; 403 — запрещённый origin; 409 — повтор actionId с другим телом; 413 — тело больше 4096 байтов; 415 — неверный Content-Type; 422 — недопустимый ход/чужой или уже активный стол либо `insufficient_funds`; 503 — временная ошибка сервиса. Ошибка не содержит внутреннего состояния.

## Повторы и два устройства

До отправки клиент сохраняет полный запрос, включая `actionId`. После неизвестного исхода он повторяет **тот же запрос**, а не генерирует новое действие. Квитанция сохраняется атомарно с состоянием; одинаковый повтор возвращает исходный ответ, даже если другой запрос уже продвинул стол дальше. Поэтому после восстановления квитанции клиент перечитывает `load` и не должен откатывать отображение на меньшую ревизию.

Одна транзакция CAS сравнивает ревизию, сохраняет состояние, денежное изменение и квитанцию. Повторный UUID стола не позволяет ещё раз списать вход или начислить результат. При конфликте клиент получает актуальную публичную проекцию, показывает изменившийся стол и просит выбрать ход заново. Не нужно переносить или объединять карточные состояния на клиенте.

## Развёртывание и граница доверия

Базовая версия была опубликована 25 октября 2026 года: миграция `20261025091820_server_durak_actions.sql`, Edge Function `server-durak` со статусом ACTIVE и `verify_jwt: true`. Расширение со входом за 100 V развёрнуто в тот же день: миграция `server_wallet` применена, `server-durak` обновлён до v2, затем до v3 с автоматическим завершением после выхода игрока, `server-wallet` v1 ACTIVE. Исходный файл миграции — `20261025110000_server_wallet.sql`; версия в рабочей БД — `20261025105819`. Метаданные прав подтверждают запрет RPC для браузерных ролей и разрешение для `service_role`. Это не означает, что проверен настоящий вход и перенос партии пользователя между телефоном и ПК: такая проверка ещё требует его сессии на обоих устройствах.

Воспроизводимая локальная SQL-проверка использует `@electric-sql/pglite@0.3.14`, изолированную память и настоящие роли Postgres. Установить эту фиксированную версию в отдельный каталог, затем запустить `node scripts/test-server-durak-sql.cjs /absolute/path/to/node_modules/@electric-sql/pglite`. Если пакет доступен обычному Node resolution, аргумент можно опустить. Скрипт не читает сетевые настройки или секреты, не обращается к production и проверяет полный rollback фикстур.

1. Проверить `node --test tests/server-durak.cjs`, затем `node scripts/test-server-wallet-sql.cjs /absolute/path/to/node_modules/@electric-sql/pglite`: он проверяет оба игровых RPC, кошелёк и изоляцию от прежнего checkpoint.
2. После checkpoints и обеих миграций серверных игр применить `server_wallet`. Он добавляет отдельный кошелёк и атомарные операции в оба игровых commit RPC, сохраняя прежние сигнатуры и бесплатные партии.
3. Развернуть Edge Function `server-durak` с файлами `index.ts`, `engine.mjs`, `core.mjs`. Gateway `verify_jwt: true`: согласно текущей [документации заголовков Edge Functions](https://supabase.com/docs/guides/functions/auth-headers), проверка поддерживает пользовательские JWT с HS256 и асимметричной подписью. Дополнительно сама функция проверяет пользователя запросом к Auth `/auth/v1/user` на каждом вызове и отклоняет анонимный аккаунт. Публичный API-ключ идёт в `apikey`, а JWT пользователя — в `Authorization`.
4. Используются только встроенные серверные `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`. Новые секреты не нужны. RPC доступны только `service_role`; у браузерных ролей нет доступа к таблицам или RPC, даже если известны их названия.
5. Включать ссылку на серверный стол после успешного SQL/Edge-развёртывания. Проверить отказ без авторизации и отсутствие доступа к RPC с публичным ключом. Настоящий перенос телефон → ПК дополнительно требует входа реального пользователя на обоих устройствах; локальный стенд или тестовый JWT этого не доказывают.

Изолированный интеграционный тест связывает настоящий обработчик Edge, движок, SQL и клиент: проверены потерянный ответ входного списания и естественное завершение Дурака с одним расчётом. Это не заменяет реальный вход владельца и перенос телефон → ПК. Google остаётся выключен; актуальная подготовка OAuth описана в [AUTH_SETUP.md](AUTH_SETUP.md). Далее — приёмка настоящих устройств и перенос остальных игр на сервер. Старые монеты не конвертируются в защищённый баланс.

Для одношаговых `finish`/`take` добавлены проверки точного равенства прежней последовательности «подготовка → продолжение» для 2–4 игроков, сохранности 36 карт, единственного локального сохранения и повтора после потерянного ответа. Финальный `finish` сохраняет завершение и платный исход одной квитанцией; устаревший второй `continue` после завершения отклоняется. Учебный сценарий и загрузка прежних `roundEnd` проверяются отдельно. Полный прогон 25 октября 2026 года: 424 теста, 424 успешных, без пропусков. Команды: `node --test tests/*.cjs`, `node scripts/sync-server-durak-core.cjs --check`; интеграция — `node scripts/test-server-economy-integration.cjs /absolute/path/to/node_modules/@electric-sql/pglite`.

26 октября 2026 года опубликован `server-durak` v5, ACTIVE, `verify_jwt: true`. Публичный ответ теперь включает `roundLimit`: `null` до первой атаки, затем фактический лимит раунда. В конце партии он может быть меньше шести. Клиент показывает этот предел в счётчике и объяснении недоступной карты; для старых квитанций без поля выводит его из публичного размера руки защитника и числа защит на столе. Скрытые карты не раскрываются. Недоступные карты и карты на паузе не перехватывают вертикальную прокрутку; перетаскивание доступных карт сохранено. Полный прогон: 452 теста, 452 успешных, обе проверки соответствия серверных ядер пройдены.
