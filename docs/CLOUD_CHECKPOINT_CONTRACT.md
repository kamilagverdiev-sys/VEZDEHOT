# Облачное продолжение партий: контракт v1

Обновлено 26 октября 2026 года. Добавлен доступ только для чтения к локальным архивам; формат облачного RPC и правила записи не изменены.

Миграция: `20261025085358_atomic_player_checkpoints.sql`. Клиент использует Supabase session постоянного аккаунта и два RPC. Гость остаётся локальным. `user_id` берётся только из `auth.uid()`; anonymous Auth не допускается.

## Чтение

```js
supabase.rpc('load_player_checkpoint', { p_known_ids: resultIds })
```

Ответ: `{status: 'ok', revision, snapshot, updatedAt, completedIds}`.

- `revision` — общая серверная версия аккаунта. До первого commit равна `0`.
- При revision `0` snapshot собирается из существующего профиля и последних 30 результатов; у нового аккаунта баланс `10000`, остальные счётчики `0`. Все пять игр — `null`.
- `updatedAt` — время сервера в ISO-формате или `null`, если профиля ещё нет.
- `completedIds` — объединение последних 30 ID и найденных в серверном журнале `p_known_ids`. Они могут включать результат старше видимой истории. Это не список всех результатов аккаунта.
- `p_known_ids` — одномерный массив, максимум 500 непустых ID длиной до 100 символов. По умолчанию `[]`.

## Запись

```js
supabase.rpc('commit_player_checkpoint', {
  p_expected_revision: baseRevision,
  p_mutation_id: mutationId,
  p_snapshot: snapshot,
  p_results: unsentResults
})
```

Ответ: `{status: 'saved' | 'conflict' | 'duplicate_result', revision, mutationId, updatedAt}`.

- `saved`: весь snapshot, зеркало `profiles`, новые `player_results` и квитанция записаны одной транзакцией. **Баланс snapshot уже содержит начисления; RPC не добавляет `delta` повторно.**
- `conflict`: версия сервера отличается; ни одна часть запроса не записана. Загрузить актуальный snapshot отдельным load. Не объединять кошелёк одной версии с партиями другой.
- `duplicate_result`: хотя бы один ID из `p_results` уже существует для этого аккаунта; весь запрос отклонён. Клиент запрашивает `completedIds` и разрешает ситуацию до новой записи. Нельзя просто удалить результат из batch, сохранив повторное начисление в snapshot.
- Повтор **того же запроса** с тем же UUID возвращает первоначальную квитанцию `saved`, даже если сервер затем принял другие изменения. Это не означает, что возвращённая revision сейчас последняя. При необходимости вызвать load.
- UUID нельзя переиспользовать с изменёнными expected revision, snapshot или results: SQLSTATE `22023`. Сохранять исходное тело незавершённого запроса локально до ответа.
- Формат/размер/значения проверяются до DML: `22023`. Недостаточная авторизация: `42501`. Остальные ошибки базы также откатывают всю транзакцию.

## Snapshot

```json
{
  "format": "vezdehot-account-checkpoint",
  "version": 1,
  "profile": {
    "nick": "Игрок",
    "balance": 10000,
    "xp": 0,
    "wins": 0,
    "games": 0,
    "bonusAt": 0,
    "avatar": "✦",
    "durakPace": "calm",
    "reduceMotion": false,
    "history": [],
    "resultIds": []
  },
  "games": {
    "durak": null,
    "bunker": null,
    "poker": null,
    "mafia": null,
    "monopoly": null
  }
}
```

Все указанные ключи обязательны; лишние ключи envelope/profile/games отклоняются. Каждая игра — объект состояния или `null` (нет партии/явное удаление). Структуру конкретной игры дополнительно проверяют клиентские валидаторы до запуска движка.

Ограничения: snapshot до 3 MiB JSONB-текста, отдельная игра до 512 KiB; history до 30; resultIds до 500 уникальных ID. Nick — 1–24 символа без крайних пробелов и управляющих символов. Счётчики — целые 0…2 000 000 000, wins ≤ games; bonusAt — целое 0…9 007 199 254 740 991. Avatar — один из `✦ ◈ ♠ ✿ △ ☾ ✹ ◇`; durakPace — `calm`, `normal`, `quick`; reduceMotion — boolean. В legacy-зеркале `profiles.nickname` однобуквенное имя получает `!` из-за существующего ограничения длины; snapshot сохраняет исходное имя.

## Результаты

`p_results` — массив до 500 записей, общий размер до 512 KiB:

```json
{"id":"stable-result-id","game":"poker","win":true,"delta":250,"xp":80,"at":"2026-10-23T12:00:00.000Z"}
```

Обязательны ровно эти шесть ключей. ID — непустая строка до 100 символов без управляющих символов; game — одна из пяти игр; win — boolean; delta — целое −2 000 000…2 000 000; xp — целое 0…2 000 000 000; at — корректная ISO-дата с часовым поясом. В одном batch ID не повторяются.

History содержит те же поля, дополнительно допускает boolean `synced`. При принятии snapshot его history нормализуется к `synced: true`. Все ID history и нового batch должны быть в `profile.resultIds`; если один ID есть в history и batch, данные должны совпадать. `p_results` не содержит `synced`.

Для покера стабильный ID расчёта относится ко всему столу. Начало с входным списанием, checkpoint и окончательный cashout должны сохраняться согласованными snapshot; перенос одной раздачи отдельно от стола недопустим.

## Архив местной ветки

Перед заменой местного состояния облачным клиент записывает полную прежнюю ветку в `vezdehot:checkpoint:v1:<scope>:archive:<uuid>`. Значение содержит `version: 1`, `createdAt`, `scope`, `snapshot`, `pendingResults` и `meta` — прежние revision, heads, неподтверждённый запрос и время подтверждения. Архив и журнал импорта должны успешно сохраниться до первой замены игры или профиля. При нехватке места замена не начинается либо остаётся под восстановительным журналом и запретом игровых действий.

В профиле доступен раздел «Архивы на устройстве», а в состоянии конфликта или ошибки — «Открыть архивы». Он показывает дату, имя, баланс практики, состав пяти сохранений и число неподтверждённых результатов. Это исторический баланс копии, а не текущий серверный кошелёк. Гостю объясняется, почему архивов облачной замены у него нет.

`VEZDEHOT.getCheckpointArchives()` перечисляет только копии активного аккаунта. `VEZDEHOT.exportCheckpointArchive(uuid)` возвращает независимую проверенную копию выбранного envelope либо `null`; `VEZDEHOT.openArchives()` открывает интерфейс. Проверяются scope, UUID ключа, версия, профиль, все пять игровых состояний, результаты и метаданные возможного незавершённого запроса. Игровые codecs проверяют копии данных: скачивание сохраняет исходные значения архива, включая состояние паузы и отметки history, без их нормализации. Устаревший обработчик после смены аккаунта или потери управления вкладкой не может скачать прежний архив.

Просмотр и экспорт не вызывают `capture`, RPC, запись профиля/игр или повтор результата; не меняют серверный баланс. Повреждённые копии пропускаются с сообщением и остаются в хранилище. Чтение ограничено 100 копиями и бюджетом 16 × 1024² единиц UTF-16 JSON-текста за просмотр, отдельная копия — 8 × 1024²; неполный список обозначается явно. Обработанные копии сортируются по дате от новых к старым. Архивы принадлежат конкретному браузеру и origin, не синхронизируются и не удаляются при просмотре.

Скачанный файл не восстанавливается автоматически. Управляемый возврат архивной ветки в игру остаётся отдельной задачей: нельзя подменить текущий snapshot или вернуть неподтверждённый результат без правил согласования версий и расчёта. Просмотр/экспорт не делает прежнюю ветку актуальной облачной версией.

Проверки: `tests/platform-archives.cjs` подтверждает изоляцию аккаунтов, обработку повреждений и ограничений, неизменность данных и отсутствие RPC, точность экспорта, защиту устаревшего обработчика и управление фокусом. Интеграционный сценарий использует настоящий `acceptCloud`: местная ветка архивируется до установки другой облачной версии и затем доступна для чтения. Полный локальный прогон 26 октября: `node --test tests/*.cjs` — **452 теста, 452 успешных**, без пропусков; настоящая проверка телефона и ПК этим не заменяется.

## Доступ и развёртывание

Привилегированное ядро и таблицы находятся в `vezdehot_private`, неэкспонируемой схеме. Обе точки входа проверяют постоянный аккаунт. Публичные обёртки — `SECURITY INVOKER`, `EXECUTE` разрешён только `authenticated`; приватное ядро имеет фиксированный пустой `search_path`. Таблицы закрыты для клиентов, RLS владельца добавлен как дополнительная защита. Серверные ключи клиенту не нужны.

Миграция отзывает прямые клиентские записи `profiles/player_results`, сохраняя чтение с существующим RLS. Развёртывать вместе с новым клиентом. Старые страницы получают безопасную ошибку записи и сохраняют локальную копию; они больше не могут обойти серверную revision.

Квитанции не удалять по возрасту: повтор старого mutation должен оставаться идемпотентным. Никакой результат не рассчитывается заново из последних 30 строк. Это защита согласованности сохранений; сервер пока не подтверждает честность клиентского игрового движка.

Проверка: `tests/cloud-checkpoint.sql` выполняется целиком в одной сессии от postgres, с остановкой при первой ошибке. Использует изолированные случайные fixture-аккаунты, реальные роли и завершающий `ROLLBACK`. Проверяет CAS, квитанции, повторный результат вне последних 30, изоляцию аккаунтов, доступ и атомарность.
