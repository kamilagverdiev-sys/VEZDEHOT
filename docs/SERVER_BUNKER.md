# Серверный Бункер

Релиз от 27 октября 2026 года. Контракт описывает отдельный серверный режим. В рабочей базе применена миграция `server_bunker_actions` (версия `20261027092153`; исходник `20261027091726_server_bunker_actions.sql`). Edge Function `server-bunker` v1 и обновлённая `server-wallet` v2 активны, обе с `verify_jwt: true`. Проверены закрытые права RPC и RLS новых таблиц: браузерные роли не имеют доступа, сервисная роль имеет. Проверка advisors не выявила новых замечаний по этому расширению; прежние замечания проекта не относятся к новым таблицам.

## Партия и правила

За столом один человек и пять ботов. В убежище три места. У каждого кандидата шесть характеристик: профессия, здоровье, хобби, багаж, фобия и факт. В одной раздаче нет одинаковой характеристики одной категории у разных кандидатов. Игрок заранее видит свои карты, но соперники учитывают только раскрытые характеристики.

Сохраняются десять сценариев и три уровня сложности обычного Бункера. У сценариев пять механических приоритетов; разные истории с одинаковым приоритетом не создают дополнительных скрытых бонусов. Сценарий добавляет +2 к подходящей характеристике, событие текущего раунда — +3. Бонусы складываются. Боты сохраняют разные подходы: текущая польза, редкие навыки команды и приоритет раунда.

Правила раздачи, выбора ботов и переходов фаз генерируются из канонического Бункера в `dist/index.html`. Серверная обёртка проверяет разрешённые действия, целостность сохранения и экономику. Генератор `scripts/sync-server-bunker-core.cjs` создаёт `supabase/functions/server-bunker/core.mjs`; `--check` выявляет расхождение с исходными правилами. Сервер использует криптографический источник случайности, не меняя глобальный `Math.random`.

В каждом раунде:

1. `reveal`: игрок выбирает одну свою закрытую характеристику и отдельно подтверждает раскрытие. Сервер раскрывает по одной карте каждого живого бота.
2. `vote`: игрок выбирает живого соперника и подтверждает голос. Сервер определяет остальные голоса; каждый живой кандидат голосует один раз и не может голосовать против себя.
3. `voteResult`: ровно один кандидат выбывает. Видны фактические бюллетени, итоговый счёт и результат равной жеребьёвки между лидерами, если голоса разделились. Эта пауза не пропускается автоматически.
4. `continue`: начинается следующий раунд либо завершается партия. Исключение человека сразу определяет поражение; оставшиеся раунды ботов не доигрываются. Если человек остаётся среди трёх кандидатов, это победа.

Добровольный выход завершает незавершённую партию без награды. Если последнее голосование уже определило победу или поражение, `resign` сохраняет этот заработанный исход так же, как `continue`, а не превращает его в сдачу. Новую партию нельзя начать поверх активной. Повторная партия создаёт новый UUID; прежние карточки не переносятся.

## Что видит клиент

Публичная проекция содержит собственные шесть полных карт, раскрытые характеристики соперников, текущий сценарий и только текущее событие. Закрытая карта бота содержит лишь `{type, icon, label, revealed:false}`. Её название, базовый балл, теги и будущие события не передаются браузеру даже после окончания партии.

Раскрытые карты содержат `revealedRound`. Отображаемые `card.value` и `player.score` относятся к текущим публичным приоритетам; баллы соперника считаются только по открытым характеристикам. Это условная игровая оценка, не оценка ценности человека. Голоса становятся публичными после голосования; тайного чтения чужих карточек при выборе ботами кандидата нет.

Выбранная, но не подтверждённая карта или кандидат — локальное состояние интерфейса. Сервер не считает такой выбор ходом. При конфликте версий или восстановлении страницы интерфейс предлагает выбрать действие заново по свежему состоянию.

## API

`POST https://cyzbraifdkrqicdsbuwe.supabase.co/functions/v1/server-bunker`

Нужны JSON, публичный `apikey` проекта и `Authorization: Bearer <access_token>` постоянного аккаунта. Edge дополнительно проверяет пользователя через Auth; анонимные аккаунты не принимаются. Разрешены production-origin Vercel и Sites. Серверный секрет не входит в клиентский код. Лишние поля запроса и действия запрещены.

| Операция | Тело запроса |
| --- | --- |
| Загрузить партию | `{ "op": "load" }` |
| Новая партия | `{ "op": "start", "actionId": "UUID", "expectedRevision": 0, "difficulty": "normal", "scenarioChoice": "random", "stake": 0 }` |
| Раскрыть характеристику | `{ "op": "action", "actionId": "UUID", "expectedRevision": 1, "gameId": "TABLE_UUID", "action": { "type": "reveal", "cardType": "profession" } }` |
| Голосовать против места 2 | Тот же конверт, `action: { "type": "vote", "target": 2 }` |
| Продолжить после голосования | Тот же конверт, `action: { "type": "continue" }` |
| Завершить партию | Тот же конверт, `action: { "type": "resign" }` |

`difficulty`: `easy`, `normal`, `hard`. `scenarioChoice`: `random` (также по умолчанию при отсутствии поля) или точный код одного из десяти сценариев. `cardType`: `profession`, `health`, `hobby`, `baggage`, `phobia`, `fact`. `target` — целое место 1–5; место 0 принадлежит человеку. Сервер проверяет фазу, раскрытие карты и то, что выбранный кандидат ещё участвует.

Ответ: `{status: "ok" | "saved" | "conflict", revision, game}`. Пока партия не создана, `game:null`. Ревизия монотонна для серверного Бункера аккаунта и не сбрасывается при повторной партии. Публичная игра включает `id`, `version`, `phase`, `round`, `difficulty`, `scenarioChoice`, `scenario`, `currentEvent`, `players`, `votes`, `lastVote`, `voteLog`, `eliminated`, `message`, `over`, `result`, `resigned`, `economy` и `legal`.

`legal:{actions,cards,targets}` перечисляет доступные сейчас действия, типы карт и места кандидатов. Это подсказка для интерфейса; каждый запрос повторно проверяется сервером. `result` равен `null`, `survived` или `lost`. `over` означает окончание всей партии, а не отдельного голосования.

## Сохранение и расчёт

Миграция `20261027091726_server_bunker_actions.sql` создаёт `vezdehot_private.server_bunker_games` и `server_bunker_receipts`. Состояния и квитанции находятся в закрытой схеме, отдельно от обычного клиентского Бункера. `server_bunker_read` и `server_bunker_commit` доступны только сервисной роли; UID берётся из подтверждённого пользователя Auth. Клиент не может подставить чужой аккаунт, колоду характеристик, результаты голосов, выигрыш или выплату.

Точная мутация сохраняется в браузере до отправки. После потерянного ответа повторяются прежний `actionId` и прежнее тело. Одинаковый UUID с другим запросом отклоняется. Два клиента не могут записать разные действия поверх одной ревизии. Получив старую квитанцию, клиент запрашивает актуальный `load`, чтобы не откатить более новый ход другого устройства.

Бесплатная практика включена по умолчанию. Вход за 100 V необязателен и использует общий [серверный баланс](SERVER_ECONOMY.md):

| Итог платной партии | Возврат | Изменение с учётом входа | XP |
| --- | ---: | ---: | ---: |
| В финальной тройке | 250 V | +150 V | 120 |
| Исключён голосованием | 0 V | −100 V | 25 |
| Добровольный выход до определённого результата | 0 V | −100 V | 0 |

Бесплатная партия не меняет баланс, XP или статистику. Списание, итоговая выплата, состояние и квитанция записываются атомарно. Повтор запроса не создаёт второй вход или второй итог. При недостатке монет HTTP 422 `insufficient_funds` не меняет ни партию, ни баланс. Свежий кошелёк загружается отдельно от игрового ответа.

Старый клиентский Бункер, его баланс практики и сохранённые партии остаются доступны отдельно. Они не импортируются как доверенный результат и не пополняют серверный кошелёк.

## Проверки и ограничения

Основные команды проверки:

```sh
node scripts/sync-server-bunker-core.cjs --check
node --test tests/server-bunker-engine.cjs tests/server-bunker-endpoint.cjs tests/server-bunker-client.cjs tests/server-bunker-ui.cjs
node scripts/test-server-bunker-sql.cjs /absolute/path/to/node_modules/@electric-sql/pglite
node scripts/test-server-bunker-integration.cjs /absolute/path/to/node_modules/@electric-sql/pglite
```

Проверки охватывают полные партии на трёх сложностях, допустимость действий, скрытую информацию, открытые бюллетени, целостность раундов, сохранение результата при выходе после последнего голосования, восстановление запроса, конфликт версий, принадлежность аккаунту и однократную экономику. SQL исполняется в одноразовой изолированной базе без реальных данных игроков. Отдельный прогон движка и HTTP-обработчика: 30 тестов прошли. Он включает отказ при фиктивном завершении с пятью живыми кандидатами и восстановление после изменения порядка ключей JSONB. Генерация правил проверена на совпадение. Полный прогон — 515 успешных тестов. Отдельно прошли SQL-наборы всех трёх серверных игр и кошелька, а также интеграция настоящего клиента, Edge-обработчика, движка и SQL: потерянные ответы, устаревшая ревизия, победа, поражение, однократный расчёт и бесплатная практика. На изолированном браузерном стенде проверены 320×568, 390×844, 844×390 и 1440×900: выбор с подтверждением, журнал голосов, восстановление после загрузки, завершение и повторная партия. Горизонтального переполнения нет.

Это одиночная игра с ботами, без комнат с друзьями и чата. Серверному режиму нужна сеть: при неопределённом ответе новые действия ждут подтверждения прежнего. Реальные Google-вход и сохранение сессии на обоих production-origin уже проверены для платформы; это не подтверждает прохождение Бункера или перенос между физическими телефоном и ПК. Браузерный стенд и SQL-тесты не заменяют проверку реальных физических устройств. Перенос телефон → ПК остаётся отдельным шагом.
